# A–L 场景端到端演示脚本与状态流转

> 版本：v0.1  
> 数据性质：全部订单、政策、金额、SLA、供应商回复和处理结果均为 Mock  
> 目标：作为前端交互、Agent Workflow、Mock API、状态持久化和端到端测试的共同输入

## 1. 统一流程骨架

十二个场景共享同一个 Agent，不为每类问题创建独立 Agent：

```text
START
→ 安全预检与意图识别
→ ORDER_SELECTION_REQUIRED
→ ORDER_CONFIRMED
→ 读取订单、政策、支付、退款和历史售后事实
→ FACTS_REQUIRED / DECISION_READY
→ 规则与风险路由
→ OPTION_PRESENTED / WAITING_EXTERNAL / TRACKING_REFUND / ESCALATED
→ RESOLVED
```

### 1.1 会话状态

| 状态 | 含义 | 允许的主要动作 |
| --- | --- | --- |
| `START` | 新任务或恢复会话 | 安全预检、识别意图 |
| `INTENT_READY` | 已识别主任务与紧急度 | 查找候选订单 |
| `ORDER_SELECTION_REQUIRED` | 需要用户确认订单 | 选择订单 |
| `ORDER_CONFIRMED` | 订单已显式确认 | 读取业务事实 |
| `FACTS_REQUIRED` | 缺少会改变结论的信息 | 最少追问、提交必要材料 |
| `DECISION_READY` | 信息足够，可进行规则判断 | 生成可选方案 |
| `OPTION_PRESENTED` | 已展示方案 | 用户选择方案 |
| `CONFIRMATION_REQUIRED` | 写操作等待二次确认 | 确认或返回 |
| `ACTION_IN_PROGRESS` | 写 Tool 已调用，等待确定回执 | 查询幂等结果 |
| `WAITING_EXTERNAL` | 等待酒店、供应商、支付或人工 | 查进度、超时升级 |
| `TRACKING_REFUND` | 退款已创建但尚未到账 | 查询支付状态 |
| `RESOLVED` | 用户目标已正确闭环 | 查看结果、反馈 |
| `ESCALATED` | 已完整移交人工或专席 | 查看工单状态 |
| `ABANDONED` | 用户主动放弃当前会话 | 保留业务案件状态 |

### 1.2 案件状态

`NEW → ASSESSING → AWAITING_USER / AWAITING_EVIDENCE / AWAITING_SUPPLIER / AWAITING_PAYMENT / AWAITING_SPECIALIST → OPTION_READY → APPROVED / REJECTED → ACTION_SUBMITTED → REFUND_INITIATED / CHANGE_SUBMITTED / RECOVERY_IN_PROGRESS / MANUAL_REVIEW → REFUNDED / CHANGED / RECOVERED / CLOSED`

会话结束不等于案件关闭；供应商、支付或人工仍在处理时，案件保持未完成状态。

### 1.3 每一步的演示字段

演示模式只展示可审计事实，不展示模型隐性推理：

- `workflow_node`：当前节点；
- `actor`：LLM、规则引擎、Tool 或人工；
- `confirmed_facts`：本步新增事实；
- `policy_or_rule`：使用的政策或硬规则；
- `tool_call`：工具名、状态和结果摘要；
- `state_transition`：会话与案件状态变化；
- `user_visible_result`：C 端实际看到的内容；
- `next_action`：用户或系统下一步。

## 2. A：条款内免费取消

**演示输入**：“帮我取消明天去杭州的酒店。”  
**核心订单**：`ORD-A-001`，应付 ¥688，仍在免费取消期。  
**展示能力**：确定性报价、二次确认、幂等写入、退款状态创建。

| 步骤 | 执行者与动作 | Tool / 规则 | 状态变化 | 用户界面与下一步 |
| --- | --- | --- | --- | --- |
| A1 | LLM 识别 `CANCEL_REFUND` | 安全预检通过 | `START → INTENT_READY` | 告知正在查找相关订单 |
| A2 | 用户确认杭州订单 | `list_user_orders` | `→ ORDER_CONFIRMED` | 展示酒店、日期、房型、金额 |
| A3 | 并行读取订单和成交政策 | `get_order_detail`、`get_policy_snapshot` | `case: NEW → ASSESSING` | 不展示最终承诺 |
| A4 | 规则引擎计算报价和权限 | `calculate_refund_quote`、`validate_action_permission` | `→ OPTION_PRESENTED` | 显示可退 ¥688、扣费 ¥0、预计 1–3 个工作日 |
| A5 | 用户确认不可逆操作 | 确认 token，有效期 10 分钟 | `→ CONFIRMATION_REQUIRED` | 唯一主按钮“确认取消并申请退款” |
| A6 | 写 Tool 执行并返回回执 | `submit_cancellation` + `idempotency_key` | `→ ACTION_IN_PROGRESS → TRACKING_REFUND`；`case → REFUND_INITIATED` | 展示订单已取消、退款单 `RFD-A-001` |

**成功终点**：订单状态 `CANCELLED`，退款状态 `REFUND_INITIATED`；不是“已到账”。  
**失败兜底**：写操作超时先调用 `get_action_result`，不得直接重复提交。

## 3. B：明确扣费取消

**演示输入**：“今天不去了，取消要扣多少钱？”  
**核心订单**：`ORD-B-001`，总价 ¥1,200，当前取消扣首晚 ¥600。  
**展示能力**：费用透明、用户决策支持、取消与保留订单并列。

| 步骤 | 执行者与动作 | Tool / 规则 | 状态变化 | 用户界面与下一步 |
| --- | --- | --- | --- | --- |
| B1 | 识别取消与价格询问 | LLM 结构化输出 | `START → INTENT_READY` | 请求确认订单 |
| B2 | 确认订单并读取阶梯政策 | 订单、政策 Tool | `→ ORDER_CONFIRMED → DECISION_READY` | 显示当前截止时点 |
| B3 | 计算应退、扣费和优惠分摊 | `calculate_refund_quote` | `→ OPTION_PRESENTED` | 显示已付 ¥1,200、扣费 ¥600、预计退 ¥600 |
| B4 | 用户选择“保留”或“取消” | 状态机 | 保留：`→ RESOLVED`；取消：`→ CONFIRMATION_REQUIRED` | 不默认替用户选择损失方案 |
| B5 | 确认后执行取消 | `submit_cancellation` | `→ TRACKING_REFUND` | 展示退款单和到账预期 |

**成功终点**：用户在明确损失后作出选择；保留订单也属于正确闭环。  
**失败兜底**：政策版本或金额工具失败时禁止展示模型估算金额。

## 4. C：已退款未到账

**演示输入**：“三天前说退了，怎么还没收到？”  
**核心订单**：`ORD-C-001`，退款 `RFD-C-001` 已发起，微信渠道处理中。  
**展示能力**：区分“发起退款”和“资金到账”，判断 SLA，自动升级。

| 步骤 | 执行者与动作 | Tool / 规则 | 状态变化 | 用户界面与下一步 |
| --- | --- | --- | --- | --- |
| C1 | 识别 `REFUND_STATUS` | LLM + 订单线索 | `START → INTENT_READY` | 请求确认已取消订单 |
| C2 | 查询退款单和支付事件 | `get_refund_status`、`get_payment_events` | `→ TRACKING_REFUND`；`case → AWAITING_PAYMENT` | 展示申请、发起、渠道处理中时间线 |
| C3 | SLA 计算 | 渠道规则 `POL-REFUND-SLA-001` | SLA 内：状态不变 | 告知等待微信、最晚更新时间、无需用户操作 |
| C4 | 用户开启到期自动升级 | `schedule_deadline_action` | `→ WAITING_EXTERNAL` | 展示超时后会自动创建支付调查工单 |
| C5 | 切换异常分支 | `create_payment_investigation` | `→ ESCALATED`；`case → MANUAL_REVIEW` | 显示财务工单 `FIN-C-001` |

**成功终点**：用户知道钱在哪、在等谁、何时更新、超时后会发生什么。  
**失败兜底**：支付状态为 `STATUS_UNKNOWN` 时明确未知并建调查单。

## 5. D：到店前无房或临时加价

**演示输入**：“酒店刚通知没房，让我加 300 元换房。”  
**核心订单**：`ORD-D-001`，入住前 5 小时，酒店反馈无法按原价履约。  
**展示能力**：紧急路由、保障规则、替代住宿、平台责任链。

| 步骤 | 执行者与动作 | Tool / 规则 | 状态变化 | 用户界面与下一步 |
| --- | --- | --- | --- | --- |
| D1 | 识别履约异常和高紧急度 | 安全分类器 | `START → INTENT_READY`；风险 `L3` | 明确按紧急住宿问题处理 |
| D2 | 确认订单与酒店通知 | `verify_fulfillment_issue` | `→ ORDER_CONFIRMED`；`case → ASSESSING` | 展示已核实与仍待核实内容 |
| D3 | 并行查替代房和保障上限 | `get_alternative_hotels`、`get_guarantee_quote` | `→ OPTION_PRESENTED` | 提供协调原酒店、替代酒店、取消保障三种动作 |
| D4 | 用户选择替代住宿 | `reserve_mock_alternative` 仅锁定 Mock 库存 | `→ ACTION_IN_PROGRESS`；`case → RECOVERY_IN_PROGRESS` | 明确差价是否需确认 |
| D5 | 人工专员确认方案 | `create_human_handoff` | `→ ESCALATED` | 显示专员 SLA、已携带事实和工单号 |

**成功终点**：在入住前给出可执行住宿方案，退款与责任结算作为后续案件。  
**失败兜底**：无替代库存时立即转专员，不让用户继续普通问答。

## 6. E：到店后无房

**演示输入**：“我已经在前台了，他们说没有我的房间。”  
**核心订单**：`ORD-E-001`，入住当日，用户已到店。  
**展示能力**：最高优先级恢复、并行 Tool、Human-in-the-loop。

| 步骤 | 执行者与动作 | Tool / 规则 | 状态变化 | 用户界面与下一步 |
| --- | --- | --- | --- | --- |
| E1 | 识别 `user_on_site=true` | L3 硬路由 | `START → ORDER_SELECTION_REQUIRED` | 紧急页替代普通售后入口 |
| E2 | 一次确认订单和可联系号码 | 订单 Tool | `→ ORDER_CONFIRMED` | 不追问退款偏好等次要信息 |
| E3 | 酒店核验、替代房搜索、人工接入并行 | `verify_fulfillment_issue`、`get_alternative_hotels`、`create_human_handoff` | `→ ESCALATED`；`case → RECOVERY_IN_PROGRESS` | 显示三项并行进展 |

**核心订单**：`ORD-F-001`，总价 ¥1,280，提前 12 天申请，政策为不可直接取消。  
**展示能力**：多轮补全、供应商协商、方案比较、外部状态追踪。

| 步骤 | 执行者与动作 | Tool / 规则 | 状态变化 | 用户界面与下一步 |
| --- | --- | --- | --- | --- |

| F2 | 查询政策快照、显著提示和历史售后 | 订单、政策、事件 Tool | `→ ORDER_CONFIRMED → FACTS_REQUIRED` | 明确“当前不能直接自动退款” |
| F3 | 只追问原因和期望方案 | LLM + 必填规则 | `case → AWAITING_USER` | 全退、部分退或改期，最多问两个问题 |
| F4 | 生成结构化协商草稿 | `build_supplier_case_draft` | `→ CONFIRMATION_REQUIRED` | 用户确认提交内容，不承诺结果 |

**失败兜底**：协商超时、拒绝或政策冲突时携完整上下文转人工复核。

**演示输入**：“航班取消了，能不能凭证明免费退？”  
**核心订单**：`ORD-G-001`，不可直接取消，行程与酒店日期关联。  
**展示能力**：最少材料、结构化证据、人工审核、避免保证全退。

| 步骤 | 执行者与动作 | Tool / 规则 | 状态变化 | 用户界面与下一步 |
| --- | --- | --- | --- | --- |
| G1 | 识别特殊原因和期望全退 | LLM | `START → INTENT_READY` | 提示材料只能触发审核 |
| G2 | 确认订单和行程时间 | 订单 Tool | `→ ORDER_CONFIRMED → FACTS_REQUIRED` | 只要求航班取消证明和乘机人关联信息 |
| G3 | 用户上传材料 | `submit_evidence_metadata` | `case → AWAITING_EVIDENCE` | 展示用途、最小必要字段和隐私说明 |

| --- | --- | --- | --- | --- |

| K2 | 查询合同主体、供应商链路、币种和时区 | `get_responsibility_chain` | `→ ORDER_CONFIRMED`；`case → ASSESSING` | 用用户语言展示“谁收款、谁确认、谁退款” |
| K3 | 读取成交政策和汇率口径 | 政策 Tool | `→ DECISION_READY` | 不自行换算最终退款金额 |
| K4 | 创建跨境专席工单 | `create_human_handoff` | `→ ESCALATED`；`case → AWAITING_SPECIALIST` | 显示北京时间 SLA 和原币金额 |

**成功终点**：责任链和当前等待方清楚，案件进入正确专席。  
**失败兜底**：政策语言冲突、税费或汇率争议由人工裁定。

## 13. L：团队、企业或多房订单

**演示输入**：“公司订了 8 间房，只取消其中 3 间，发票怎么处理？”  
**核心订单**：`ORD-L-001`，企业协议订单，8 间房，付款人与入住人分离。  
**展示能力**：授权链、部分取消、金额拆分、企业专席。

| 步骤 | 执行者与动作 | Tool / 规则 | 状态变化 | 用户界面与下一步 |
| --- | --- | --- | --- | --- |
| L1 | 识别团体、多房和企业授权 | LLM + 风险规则 | `START → INTENT_READY`；风险 `L3` | 不进入普通单房取消流程 |
| L2 | 核对付款人、联系人和可操作房间 | `get_group_order_breakdown` | `→ ORDER_CONFIRMED → FACTS_REQUIRED` | 仅让授权人选择要处理的 3 间房 |
| L3 | 生成拆分影响预览 | `get_partial_cancel_quote` | `→ OPTION_PRESENTED` | 展示房费、优惠、税费和发票影响，暂不执行 |
| L4 | 移交企业／团体专席 | `create_human_handoff` | `→ ESCALATED`；`case → AWAITING_SPECIALIST` | 专席收到授权链、房间列表和对账摘要 |

**成功终点**：复杂订单没有被错误自动取消，用户获得可核对的拆分方案。  
**失败兜底**：授权不完整时阻断任何写操作。

## 15. 端到端验收共同要求

每个场景都必须满足：

1. 订单未经显式确认不得调用订单级写 Tool；
2. 页面金额必须来自最新 Tool 回执；
3. `REFUND_INITIATED` 不得显示为“已到账”；
4. 等待外部时必须显示等待方、SLA、下一更新时间和超时动作；
5. 所有写 Tool 都有确认 token、预期版本和幂等键；
6. 高风险场景转人工时携带订单、诉求、事实、政策、证据、动作和未决问题；
7. Mock 数据、政策、供应商回复和运营指标始终有显著标识；
8. 刷新页面后案件状态能够从持久化数据恢复；
9. Tool 失败不得被表达为业务成功；
10. 每个场景至少包含一条失败或超时回归用例。
