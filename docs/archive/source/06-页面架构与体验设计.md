# C 端页面架构、视觉优先级与预期管理设计

> 版本：v0.1  
> 日期：2026-09-04  
> 默认用户：真实 C 端消费者  
> 第二受众：在桌面端评估作品的面试官  
> 设计原则：真实用户完成任务优先，面试官理解方案通过独立解释层完成

## 1. 设计结论

产品不应以传统“满屏聊天记录”为核心，也不应做成展示功能的作品集落地页。推荐采用：

> 任务型售后界面为主体，对话负责理解输入，结构化任务区负责展示订单、方案、动作和进度。

用户进入后每个页面只完成一个目标：

1. 确认处理哪笔订单；
2. 看懂这笔订单能怎么处理；
3. 确认一个不可逆动作；
4. 跟踪正在等待的结果；
5. 在紧急情况下先解决今晚住宿。

面试官需要看的意图、政策、规则、Tool 和 trace 放入独立“演示解释层”，不与真实用户争夺视觉注意力。

## 2. 双重受众的正确关系

### 2.1 真实 C 端用户是产品用户

他们处在手机或普通浏览器中，常伴随时间、金额和情绪压力。需要快速回答五件事：

- 这是哪笔订单；
- 现在能不能处理；
- 能退多少；
- 当前在等待谁；
- 我现在要做什么。

他们不需要看到：LLM 置信度、节点名称、JSON、token、trace 原文或系统 prompt。

### 2.2 面试官是评估者，不是第二套业务用户

面试官关心：

- 为什么先做这些场景；
- Agent 是否真的查询和执行，而不是写话术；
- 模型、规则、Tool 和人工如何分工；
- 为什么某个场景自动化，另一个场景转人工；
- Mock 和真实业务边界是否诚实；
- 产品如何评测和迭代。

因此不要增加一个“面试官后台”。只需在同一页面提供只读的“查看 Agent 判断过程”开关。

### 2.3 设计验收问题

关闭演示模式后，如果一个普通消费者仍然看到任何只为证明技术而存在的信息，说明分层失败。

打开演示模式后，如果面试官还需要阅读长篇 PRD 才能理解 Agent 做了什么，说明解释层失败。

## 3. 用户规模与场景权重

### 3.1 外部数据能证明什么

- 市场监管总局披露，2025 年餐饮住宿服务投诉 119.1 万件，占服务投诉 16.6%；售后服务问题占全部消费投诉 26.3%，连续三年位居问题类型首位。该数据说明住宿售后值得投入，但不能推断去哪儿酒店退款会话结构。  
  来源：https://www.samr.gov.cn/xw/zj/art/2026/art_c669e8b73a21493b913752ca515cc261.html
- 一份基于“电诉宝”样本的 2024 年第四季度在线旅游投诉报告称，“退款问题”占其样本 44.78%，“霸王条款”占 13.43%。该样本并非全市场或酒店专属，只能支持退款、规则争议是高显著问题。  
  来源：https://www.fxbaogao.com/detail/4702914
- 公开的 119,390 条葡萄牙酒店预订数据中，取消率约 37.0%。这是预订结果而非客服意图，也不是中国市场，只说明取消并非边缘事件。  
  来源：https://pmc.ncbi.nlm.nih.gov/articles/PMC6297060/

### 3.2 用于页面排序的 Mock 场景结构

以下是假设每 100 个有效酒店退款会话的设计样本，不代表去哪儿真实数据：

| 场景 | Mock 数量 | 频次等级 | 紧急度 | 自动化潜力 | 页面策略 |
| --- | ---: | --- | --- | --- | --- |
| 条款内免费/扣费取消 | 38 | 高 | 中 | 高 | 首页第一快捷任务，方案卡优先 |
| 退款进度/未到账 | 26 | 高 | 中 | 高 | 首页第二快捷任务，直接进入时间线 |
| 不可取消例外协商 | 18 | 中 | 中高 | 中 | 作为英雄演示场景，强调预期管理 |
| 日期/姓名/房型变更 | 7 | 中低 | 中 | 中 | 作为退款替代方案出现 |
| 到店无房/临时加价 | 5 | 低 | 极高 | 低至中 | 始终保留高可见紧急入口 |
| 描述不符/服务争议 | 4 | 低 | 高 | 低 | 证据收集后转人工 |
| 支付异常/盗刷/复杂订单 | 2 | 低 | 极高 | 低 | 阻断自动处理并转专席 |

Mock 逻辑：高频的取消和进度承担主界面效率；中频的例外协商承担 Agent 核心展示；低频高损失的到店无房获得高于数量的视觉权重。

### 3.3 视觉优先级公式

页面排序不能只按人数，采用：

```text
视觉优先级 = 频次 × 任务可执行性 + 紧急度 × 用户损失 + 当前是否需要用户行动
```

因此：

- “退款进度”频次高，但如果不需要用户动作，主按钮权重应低；
- “到店无房”频次低，但紧急度和用户损失极高，入口必须持续可见；
- “查看政策全文”信息量大，但不直接推进任务，应折叠在二级层；
- “确认取消”是当前唯一不可逆动作，必须成为页面唯一主按钮。

## 4. 页面地图

### 4.1 页面而不是功能堆叠

| 页面 | 唯一主要目的 | 主操作 | 不应出现 |
| --- | --- | --- | --- |
| P0 演示入口 | 让面试官选择一个场景并理解作品边界 | 开始演示 | 完整产品说明长文 |
| P1 售后入口 | 让用户说明要解决什么问题 | 选择快捷任务或输入诉求 | Agent 技术细节 |
| P2 订单确认 | 确认唯一目标订单 | 确认这笔订单 | 退款最终承诺 |
| P3 处理方案 | 让用户看懂可选方案 | 选择一个方案 | 同时要求确认不可逆操作 |
| P4 操作确认 | 让用户确认取消/退款等写操作 | 确认执行 | 新增其他方案和营销内容 |
| P5 处理进度 | 让用户知道当前状态与下一时间点 | 设置提醒或在超时后升级 | 重复解释完整退改政策 |
| P6 紧急住宿恢复 | 让已到店用户今晚先住下 | 联系专员/选择替代住宿 | 普通 FAQ 和慢速表单 |
| P7 人工衔接 | 让用户确认已成功移交 | 进入人工会话 | 让用户重述全部事实 |

这些页面可以由同一个 SPA 路由或步骤状态实现，但视觉上每次只保留一个主要目的。

## 5. 各页面设计

### P0：面试演示入口

**目标**：30 秒内让面试官知道这是什么、为什么值得体验、从哪里开始。

**首屏信息顺序**：

1. 产品名：“酒店退款 Agent”；
2. 一句话价值：“把订单、政策、供应商协作与退款状态串成可执行流程”；
3. Mock 声明；
4. 推荐演示：“不可取消订单协商，约 3 分钟”；
5. 其他三个场景文本入口；
6. “查看研究与方案”作为弱链接。

**唯一主按钮**：“开始推荐场景”。

不要放虚构业务指标、个人大段介绍、技术 logo 墙或四个等大功能卡。

### P1：售后入口

**目标**：让真实用户快速表达问题。

**信息顺序**：

1. 标题：“这笔酒店订单遇到了什么问题？”；
2. 三个高频任务：“取消并退款”“查询退款进度”“酒店无法入住”；
3. 自由输入框：“也可以直接描述情况”；
4. 紧急入口：“已经到店但无法入住”；
5. 人工客服弱入口，但始终可达。

“酒店无法入住”不应因为 Mock 数量少被藏进更多菜单。

### P2：订单确认

**目标**：避免查错或操作错订单。

只展示完成辨识所需字段：酒店名、城市、入住日期、房型、总金额和订单状态。退改详情等确认后再展示。

候选订单最多 3 个。只有一个候选也需要用户确认。主按钮：“确认处理这笔订单”。

### P3：处理方案

**目标**：让用户决定下一步，不是阅读政策。

视觉顺序：

1. 结果标题：“可以免费取消”或“当前不能直接退款，可发起协商”；
2. 核心金额：预计退回、预计扣费；
3. 状态和时间：现在尚未提交、预计到账；
4. 最多两个方案；
5. 主操作；
6. “为什么是这个结果”折叠项；
7. 订单摘要作为页面末端复核信息。

退款金额不能做成炫耀式大数字。它应清晰但与动作同属一个任务块。

### P4：操作确认

**目标**：明确不可逆后果，获得真实确认。

页面只保留：

- 将取消哪笔订单；
- 预计退回与扣费；
- 退款路径和预计到账；
- 取消后是否不可恢复；
- 主按钮：“确认取消并申请退款”；
- 次按钮：“返回修改”。

禁止在按钮文案中使用含糊的“确定”“继续”。

### P5：处理进度

**目标**：降低用户对未知状态的焦虑。

首屏必须回答：

- 已经完成什么；
- 当前正在等待谁；
- 预计何时更新；
- 用户是否需要操作；
- 超时后平台会做什么。

不要展示虚假的百分比进度条。退款不是线性下载任务，使用事件时间线和当前节点更准确。

### P6：紧急住宿恢复

**目标**：帮助用户今晚住下，而不是先讨论退款责任。

视觉顺序：

1. 明确状态：“已按紧急住宿问题处理”；
2. 立即联系专员按钮；
3. 酒店核验状态；
4. 附近替代住宿选项；
5. 取消与保障申请；
6. 证据提示。

页面使用警示色但不制造恐慌。主动作永远是解决住宿或连接专员。

### P7：人工衔接

**目标**：让用户相信上下文已经被带走。

展示：工单号、转接原因、预计响应、已经交给人工的五项摘要、用户下一步。不要再次要求用户填写订单号和原因。

## 6. 信息层级

### 6.1 五层信息模型

| 层级 | 信息 | 视觉处理 |
| --- | --- | --- |
| L1 当前任务 | 当前结论、唯一主操作 | 页面标题区，最高对比度 |
| L2 决策关键 | 金额、状态、责任方、下一时间点 | 紧邻结论，短句和结构化数字 |
| L3 用户选择 | 方案 A/B、是否确认、是否上传材料 | 单一主按钮加一个次要选项 |
| L4 复核依据 | 订单摘要、政策引用、材料要求 | 折叠区或页面下方 |
| L5 面试解释 | 意图、槽位、规则、Tool、trace | 演示模式右侧抽屉 |

任何页面都不应同时让 L1 到 L5 竞争注意力。

### 6.2 主按钮规则

- 每页最多一个实心主按钮；
- 第二动作使用描边或文本；
- “联系人工”在普通场景中持续可见但不抢主操作；
- 在紧急、高风险或自动处理失败时，“联系人工”升级为主按钮；
- 写操作按钮必须说清动作和对象。

## 7. 预期管理设计

### 7.1 预期管理不是一段文案

每个处理状态都必须拥有五个字段：

```text
事实：已经发生了什么
状态：现在处于哪一步
责任：正在等待谁
时间：最晚何时有更新
动作：用户现在要不要做什么
```

### 7.2 状态文案矩阵

| 系统状态 | 推荐标题 | 辅助说明 | 用户动作 |
| --- | --- | --- | --- |
| 尚未提交 | 还没有取消订单 | 确认后才会提交，不会自动操作 | 确认或返回 |
| 已提交协商 | 已向供应商发起协商 | 预计今天 18:00 前回复 | 无需操作，可设置提醒 |
| 等待材料 | 需要你补充一项材料 | 仅用于判断是否符合特殊退改 | 上传或选择无材料继续 |
| 已同意退款 | 退款方案已确认 | 需要你在有效期内确认 | 选择并确认方案 |
| 已发起退款 | 平台已发起 ¥688 退款 | 资金尚未到账，微信处理中 | 无需操作 |
| 渠道处理中 | 正在等待支付渠道入账 | 预计最晚 9 月 5 日 18:00 更新 | 设置提醒 |
| 已到账 | ¥688 已原路退回 | 到账时间与退款单号可查看 | 完成评价 |
| 超过 SLA | 已超过预计到账时间 | 已自动创建支付调查工单 | 查看工单或联系人工 |
| 状态未知 | 当前无法确认退款状态 | 不会将未知结果显示为成功 | 重试或转人工 |

### 7.3 禁止的模糊表达

- “正在为您处理中”；
- “请耐心等待”；
- “大概很快到账”；
- “酒店不同意退款”，如果实际只是供应商未回复；
- “已经退款”，如果系统状态只是发起；
- “我们会尽快处理”，却没有责任方或下一时间点。

### 7.4 协商预期

例外协商页面必须明确：

- 协商不是退款承诺；
- 为什么需要酒店或供应商确认；
- 当前提交了哪些事实；
- 何时给第一次回复；
- 可能结果是全退、部分退、改期或拒绝；
- 超时后将自动升级，而不是让用户自行反复催促。

## 8. 对话设计

### 8.1 对话不是页面主体

对话负责：自由表达、澄清、解释、情绪承接。

结构化组件负责：订单、金额、状态、方案、确认和进度。

不能把关键金额和按钮埋在聊天气泡中。

### 8.2 每轮回复结构

```text
一句结论
一项关键依据或未知项
一个下一步
```

复杂政策默认折叠。一个回复最多提出两个问题，一个页面最多一个主动作。

### 8.3 情绪处理

承认影响，但不使用冗长套话：

- 到店无房：“你已经到店，我先帮你解决今晚入住。”
- 退款延迟：“平台已发起退款，但资金还没有到账。我正在核对支付渠道状态。”
- 不可取消：“这笔订单当前不能直接自动退款，我可以立即替你发起协商，但现在不能保证结果。”

## 9. 演示解释层

### 9.1 打开方式

桌面端顶部提供弱化开关：“查看 Agent 判断过程”。默认关闭。移动端放入更多菜单，不占主任务空间。

### 9.2 信息顺序

右侧抽屉按用户旅程同步展示：

1. 当前节点；
2. 意图和紧急度；
3. 已确认与缺失槽位；
4. 读取的订单事实；
5. 命中的政策版本；
6. 规则与风险判断；
7. Tool 调用和返回状态；
8. 为什么自动执行或转人工；
9. 响应事实校验结果。

### 9.3 不展示

- 完整系统 prompt；
- chain-of-thought；
- 模型内部推理文本；
- 未脱敏的用户信息；
- 大段 JSON 原文。

解释层展示结构化决策依据，不展示模型隐式思考。

## 10. 视觉方向

### 10.1 使用场景决定主题

真实用户可能站在酒店前台、机场或通勤途中，在明亮环境下单手使用手机，并处于焦虑状态。因此默认采用高可读性的浅色主题，不把“AI 工具”做成深色控制台。

### 10.2 色彩策略

采用 restrained 策略：带轻微暖度的中性背景，加一个低饱和主色用于主操作和当前状态。成功、警告、紧急分别使用克制的语义色，不使用纯黑、纯白、霓虹或大面积品牌仿色。

颜色只承担：

- 当前可执行主操作；
- 选中状态；
- 成功、警告、错误和信息状态；
- 时间线当前节点。

“Mock”“等待外部”“未知”都必须同时用文字表达，不能只靠颜色。

### 10.3 字体与密度

- 使用单一系统无衬线字体，保证中文和数字清晰；
- 页面标题 24px 左右，关键结论 20px，正文 15 至 16px，辅助信息不低于 13px；
- 金额使用等宽数字特性，不使用夸张展示字号；
- 正文单行长度控制在 65 至 75 个英文字符的等效宽度；
- 紧急页减少信息密度，进度页可以略高密度。

### 10.4 容器与层次

- 页面主体使用连续内容面和分隔线，不把每个字段做成卡片；
- 只有订单选择、方案选择和人工移交等真正独立对象使用容器；
- 禁止卡片内部继续嵌套卡片；
- 阴影只用于浮层和抽屉，普通任务块用背景层次和边框区分；
- 圆角适中且统一，不使用过度柔软的胶囊化界面。

### 10.5 动效

- 150 至 250ms，仅表达状态变化；
- 提交后立即显示确定的受理结果，再更新异步状态；
- 新时间线事件轻微淡入；
- 不使用打字机效果、弹跳、粒子或编排式页面入场；
- 支持减少动态效果。

## 11. 响应式策略

### 手机端

- 单列；
- 底部固定当前主操作，但不得遮挡内容；
- 订单和方案按完整阅读顺序展开；
- Agent 解释层默认隐藏；
- 触控目标至少 44px；
- 紧急入口在首屏可达。

### 桌面端普通用户模式

- 主任务区最大宽度约 720px，避免横向过散；
- 订单摘要可在右侧形成轻量固定栏；
- 当前主操作保持与任务上下文相邻。

### 桌面端演示模式

- 主任务区约占 60% 至 65%；
- 决策解释抽屉约占 35% 至 40%；
- 两侧节点同步高亮；
- 抽屉关闭后主任务区回到居中布局；
- 不使用手机外壳模型，避免让作品像不可操作的原型预览器。

## 12. 关键组件状态

每个组件必须覆盖默认、悬停、焦点、按下、禁用、加载、成功和错误状态。

### 主按钮

- 加载时保留原按钮宽度；
- 写操作显示具体动词；
- 工具结果未知时禁用再次提交，先查询结果；
- 焦点环清晰可见。

### 订单选择项

- 整行可点击但内部语义正确；
- 选中不仅改变背景，还显示明确勾选和“已选择”；
- 过期或不可操作订单解释原因。

### 进度时间线

- 完成、当前、等待、失败、未知五种状态；
- 每个节点显示时间或“尚未发生”；
- 不用百分比；
- 当前节点同时显示等待对象。

### 政策依据

- 默认显示一句与当前决定相关的摘要；
- 展开后显示模拟政策名称、版本和适用条件；
- 不整段倾倒知识库原文。

## 13. 页面验收清单

### 面向真实用户

- 5 秒内能找到当前结论；
- 10 秒内能找到预计退款金额或未知原因；
- 10 秒内知道当前等待谁以及何时更新；
- 每页只有一个主按钮；
- 人工入口始终可达；
- 到店无房不超过一步进入紧急处理；
- 写操作前明确二次确认；
- 退款发起与到账视觉状态明显不同；
- 用户不需要理解 Agent、RAG、Tool 或 Workflow。

### 面向面试官

- 首屏明确这是个人概念作品和 Mock；
- 30 秒内理解产品解决的问题；
- 一键进入推荐场景；
- 3 分钟内看完一次端到端 Workflow；
- 能展开查看政策、规则、Tool 和风险判断；
- 能看出为什么不是纯 FAQ；
- 能看出为什么没有把所有场景自动化；
- 能查看测试结果或评测入口；
- 不需要先读 PRD 才理解产品。

## 14. 传达目的自检

### 你的求职目的是否传达到位

正确的传达顺序应是：

1. 这是一个真实用户可以理解和操作的售后产品；
2. 它解决的是退款任务推进和预期管理，不只是回答问题；
3. Agent 的每一步由订单、政策、规则和 Tool 支撑；
4. 高风险场景有明确人工边界；
5. 你知道数据不足，并用 Mock 和评测诚实验证设计。

如果先展示模型、节点和技术栈，面试官可能只看到“会搭 Agent”。如果先展示完整 C 端任务，再打开解释层，才能同时体现需求、产品与 Agent 设计能力。

### 每个页面的“一句话测试”

在设计稿和开发评审时，要求每个页面都能补完：

> 用户来到这里，是为了 ______；完成标志是 ______。

若一个页面需要填两个主要任务，应拆分步骤或使用渐进展开。
