# SQLite、Mock API、规则引擎与可执行 Workflow

> 版本：v0.1  
> 性质：求职作品 MVP；全部业务数据与接口均为 Mock  
> 代码位置：`backend/`

## 1. 本阶段交付结论

现有 A–L 场景、Mock 数据与 33 个 Tool 契约已经从“规格”进入“可执行系统”。后端使用 FastAPI + SQLite，规则引擎为可单测的 Python 纯函数，Workflow 使用显式状态迁移，并记录节点级 Trace。

这不是接入真实去哪儿系统的生产后端。它的价值是证明四件事：

1. 产品场景能被翻译成稳定的系统状态和接口；
2. 金额、政策、权限与状态不交给 LLM 自由生成；
3. 高影响写操作具有确认、版本和幂等保护；
4. 十二种不同售后问题可以由一个 Agent 和一套 Workflow 骨架处理。

## 2. 运行时结构


## 3. SQLite 核心分区

| 数据域 | 表 | 作用 |
| --- | --- | --- |
| 业务事实 | `orders`、`policies`、`payments`、`refunds` | 形成退款判断的可信事实源 |
| 售后案件 | `cases`、`case_events`、`external_cases`、`evidence_items` | 保存跨会话业务状态 |
| Agent 状态 | `sessions`、`workflow_runs`、`workflow_steps` | 保存会话检查点和可展示 Trace |
| 安全控制 | `confirmation_tokens`、`idempotency_records` | 防止未确认、错版本和重复写入 |
| Tool 治理 | `tool_contracts`、`tool_executions` | 契约白名单与执行审计 |
| 演示数据 | `scenario_fixtures`、`fixture_catalog` | 区分初始事实和动作后的预期结果 |

业务表同时保留常用索引列与 `payload_json`：前者便于查询和约束，后者保留 Mock 契约的完整结构，减少演示阶段无意义的数据迁移成本。

## 4. 规则引擎

首版实现四组确定性规则：

- 免费取消时点：按政策快照截止时间判断 ¥688 全退；
- 阶梯扣费：按请求时点命中 ¥600 扣款档，退款 ¥600；
- 支付事件解释：区分实扣和预授权冻结，禁止把 ¥500 冻结表述为重复实扣；
- 风险与路由：A/B/C/I 为 L1，F/G 为 L2，其余复杂协同场景为 L3。

Tool 返回的 Mock fixture 可以补充报价 ID、有效期和渠道，但最终金额先经过规则纯函数计算，测试会单独验证规则结果。

## 5. 写操作权限

交易类写操作的执行顺序为：

```text
读取订单与政策
→ 生成带版本的确定性报价
→ 验证动作权限
→ 展示金额与后果
→ 签发短时 confirmation_token
→ 校验 expected_order_version
→ 使用 idempotency_key 执行写 Tool
→ 持久化业务结果与审计记录
```

同一幂等键和同一请求再次提交时返回第一次结果；同一幂等键携带不同参数时拒绝执行。确认令牌绑定 Session、Tool、订单版本和动作参数，不能跨动作复用。

## 7. 前端接入需要使用的数据

本地前端调用 FastAPI；GitHub Pages 为免安装演示，使用同响应结构的浏览器端确定性 Mock Adapter：

- 场景选择读取 `/api/scenarios`；
- 点击开始模拟调用 `/api/workflows/{scenario_id}/run`；
- C 端结果使用返回的案件状态、等待方和 Tool 事实；
- 面试官 Trace 使用 `/api/workflow-runs/{run_id}`；
- 运营看板后续从 `workflow_runs`、`workflow_steps`、`tool_executions` 和案件终态聚合。

本地模式用 API 验证 SQLite、规则、权限和 Tool 执行；在线模式用于验证交互。两种模式保持同一响应协议，且都明确标注为 Mock。
