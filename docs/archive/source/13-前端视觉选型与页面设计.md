# 前端视觉选型与页面设计

> 版本：v0.1  
> 目标：在既有三模块架构、P0–P7 任务设计和 A–L 场景基础上，确定可实施的视觉方向  
> 参考：[shadcn/ui](https://github.com/shadcn-ui/ui)、[coss](https://github.com/cosscom/coss)

## 1. 我们现在有没有前端设计

本文件记录视觉选型阶段的决策，正式 React 前端现已完成：

- 已完成：双重受众、三模块叙事、页面地图、信息层级、预期管理规则、P0–P7 低保真线框图；
- 已完成：Agent 整体流程图、A–L 场景和可执行后端；
- 已完成：统一视觉系统、组件规范、十二场景选择方式、API/浏览器 Mock 状态映射、响应式细节与最终前端实现；
- `09`、`10` 为历史草稿，已归档且不作为当前视觉基线。

当前实现以 `frontend/` 为唯一产品界面基线。

## 2. 两个参考项目分别适合什么

| 维度 | shadcn/ui | coss | 本产品选择 |
| --- | --- | --- | --- |
| 定位 | 开放组件代码与分发方式，强调自行组合和改造 | Cal.com 的官方设计系统，更完整、更有产品气质 | 两者分工使用 |
| 视觉 | 默认中性，但容易做成常见模板 | 更克制、紧凑，边框和语义状态更细腻 | 视觉参考 coss |
| 工程 | 组件可复制进项目，适合 React/Vite 与 Tailwind | 基于 Base UI，组件质量高但体系更有自身意见 | 工程底座 shadcn/ui |
| 状态 | 基础 variant 完整，可自行扩展 | 明确包含 info、success、warning、error 语义 | 采用 coss 式状态词汇 |
| 密度 | 默认适中 | 桌面端更紧凑，移动端自动增大目标 | 采用响应式密度 |
| 授权 | MIT | 仓库混合授权，`apps/ui` 等部分为 MIT | 不直接复制品牌代码，降低授权与同质化风险 |

结论：

> 使用 shadcn/ui 作为组件工程基础，使用 coss 作为简约视觉和交互状态参考，再按酒店售后任务重新设计信息层级。

不直接选择“纯 shadcn 风格”，因为容易呈现成通用 SaaS 模板；不直接套用“纯 coss”，因为本产品需要自己的退款状态、预期管理和 Agent Trace 组件。

## 3. 视觉方向

关键词：专业、克制、可信、清醒。

- 默认浅色，适应面试桌面和旅行中的移动场景；
- 冷调中性色为主体，一种克制蓝色只承担主操作和当前状态；
- 语义色面积小，永远与文字状态配合；
- 边框和背景层级代替大阴影；
- 基础圆角 8px，任务区 12px，不使用满屏药丸形组件；
- 不使用去哪儿 Logo 或官方色，明确保持个人概念作品身份；
- 不使用渐变、玻璃、霓虹、机器人头像和流光动画。

完整 token 与组件规范见 `DESIGN.md`。

## 4. 全局页面框架

产品仍保留三块，不增加冗余页面：

```text
酒店退款 Agent
Agent 设计     场景模拟     运营看板                         Mock 数据
──────────────────────────────────────────────────────────────────────
当前页面内容
```

选择顶部导航而不是永久侧边栏，原因是只有三个一级模块，侧边栏会让作品误看成传统管理后台。

页面最大宽度 1440px。主内容使用边界线和空白组织，不把所有信息塞入卡片。

## 5. 页面一：Agent 设计

唯一目的：让面试官在 60 秒内理解 Agent 如何推进真实业务状态。

### 首屏结构

```text
会话入口 + Session Memory
        ↓
LLM + 安全分类器
        ↓
用户确认唯一订单
        ↓
◇ READ Gate：是否允许读取？ ◇ ──拒绝──→ 阻断或人工核验
        │允许
        ↓
查询类 Tool → 结构化过滤 + RAG → ◇ 信息是否足够？ ◇
                                      │否 → 最少追问 → 回到 READ Gate
                                      │是
                                      ↓
                         ◇ 规则引擎选择处理路径 ◇
                    ┌────────┼──────────────┐
               只读查询   确定性交易        外部协同/高风险
                  ↓       报价→展示→确认           ↓
               状态 Tool      ↓                 WRITE Gate
                    ◇ WRITE Gate：允许改变业务状态？ ◇
                         ↓交易写入       ↓流程写入
                      交易 Tool          协同 Tool
                           └──────┬──────┘
                                  ↓
                     事实校验器 + LLM
                                  ↓
                     Case Memory + Trace Log

[开始场景模拟]
```

设计重点：

- 使用与框线稿一致的纵向完整拓扑，不再把流程压缩成五张能力摘要卡；
- 判断节点使用菱形，允许、拒绝、是、否、交易写入和流程写入直接写在线路旁；
- 最少追问必须明确回到 READ Gate，展示 Agent 如何补齐信息而不是直接猜测；
- 三条业务出口保留各自完整步骤，READ/WRITE 权限和用户确认嵌入路径；
- 结果统一进入事实校验、Case Memory 与 Trace Log，强调“执行成功”不等于“到账闭环”；
- 节点用低色度语义区分 LLM/规则、Tool、权限/人工和 Memory/Trace；
- 桌面完整展示 1180px 流程画布，移动端只在画布内横向滚动，不让整个页面溢出；
- Tool 清单只显示路径相关代表项，完整 33 个机器契约保留在开发材料中；
- 页面唯一主按钮为“开始场景模拟”。

## 6. 页面二：场景模拟

唯一目的：让面试官选择一个场景并验证端到端处理。

### 桌面布局

```text
┌ 场景 240 ┐ ┌──────── C 端任务区，最小 520 ────────┐ ┌ Trace 360 ┐
│ 取消与变更 │ │ 当前订单                              │ │ 当前节点  │
│ A 免费取消 │ │                                      │ │ 新增事实  │
│ B 扣费取消 │ │ 结论：可以免费取消                   │ │ 命中规则  │
│ F 例外协商 │ │ 预计退款 ¥688，扣费 ¥0               │ │ Tool 结果 │
│ I 订单改期 │ │                                      │ │ 状态变化  │
│ ...        │ │ 推荐方案 / 金额影响 / 必要风险        │ │            │
│            │ │                         [确认取消]    │ │            │
└────────────┘ └──────────────────────────────────────┘ └────────────┘
```

### 十二场景组织

不使用十二个横向 Tab。按用户问题组织成四组：

1. 取消与变更：A、B、F、I；
2. 退款与支付：C、J；
3. 履约与住宿：D、E、H；
4. 特殊审核：G、K、L。

默认推荐 F“不可取消例外协商”，因为它最完整地展示 LLM、政策、最少追问、供应商 Tool、等待 SLA、方案确认和退款创建。A、C、E 分别作为自动执行、状态查询和紧急兜底的快速入口。

### C 端任务区

不以聊天气泡为主体。页面顺序固定为：

1. 用户原始诉求；
2. Agent 一句话结论；
3. 推荐的可执行方案；
4. 金额、扣费与方案影响；
5. 必须说明的风险或不可逆后果；
6. 当前唯一主操作。

责任主体、内部处理状态、政策命中、证据和审计记录不向 C 端展示。用户提交后，原位置直接切换为已验证结果、后续安排和下一更新时间。

### Trace

Trace 只向面试官解释：

- Workflow 节点；
- Actor：LLM、规则、Tool、安全机制或人工；
- 确认了什么事实；
- 命中了什么规则；
- 状态如何变化。

不显示 Chain of Thought，不把完整 JSON 倾倒在界面里。

## 7. 结论与方案核心组件

这是 C 端最重要的任务组件：Agent 在后台完成核实和判断后，直接给出结论与可执行方案。

```text
不能直接退款，可以替你发起协商

✓ 推荐方案：申请例外退款协商                    提交前确认
  平台代你向酒店或供应商争取部分退款、免费改期等方案

订单金额 ¥1,280   当前可直接退 ¥0   方案影响：暂不取消订单
说明：协商可能为部分退款、免费改期或拒绝，不承诺成功

                                      [确认提交协商]
```

页面不解释 Agent 的推理过程，也不展示 Tool、规则、责任链、证据或审计记录。必要的预期管理通过“方案影响、风险说明、处理结果、下一更新时间”完成；面试官需要查看的系统依据放在独立 Trace 中，并明确标记为“用户不可见”。

## 8. 页面三：运营看板

唯一目的：定位退款任务在哪个环节流失，并推动 Badcase 修复闭环。

### 8.1 页面结构

```text
[近 8 周] [全部场景] [全部供应商] [全部风险]                 Mock 数据

正确退款任务闭环率 62.4%          健康结论：环比改善，但到账与重复进线仍是主损失
口径：结果、金额、权限和流程均正确，且取消/退款/替代方案得到系统或用户确认
────────────────────────────────────────────────────────────────────────────
退款处理链路漏斗
有效案件 10,000 → 首次有效决定 9,210 → 方案确认 8,420 → 业务状态完成 7,110
→ 到账/结果确认 6,580 → 正确闭环 6,240
────────────────────────────────────────────────────────────────────────────
核心指标矩阵
业务结果｜效率｜自动化与体验｜协作与质量｜风险
────────────────────────────────────────────────────────────────────────────
Badcase 闭环：闭环率 78.6%｜逾期 7｜复发率 4.1%
发现 → 归因 → 修复 → 回归 → 上线观察 → 关闭
Badcase 队列 + 选中问题的根因、修复、回归用例和关闭标准
```

### 8.2 北极星指标

**正确退款任务闭环率**：在结果、金额、权限和流程均正确的前提下，完成取消、退款或明确替代方案并得到系统或用户确认的有效案件数 ÷ 有效退款案件数。

北极星只承担总体结果判断，不负责解释问题。页面必须同时显示分子、分母、趋势、目标和主要损失环节。

### 8.3 处理链路漏斗

漏斗使用同一基线的水平条，避免梯形面积造成视觉误导。每层显示：

- 当前案件数；
- 相对总量转化率；
- 与上一层相比的流失数；
- 最大流失原因；
- 点击后过滤指标与 Badcase。

演示数据统一以 10,000 个有效退款案件为分母：

| 环节 | 案件数 | 总体转化率 | 环节流失 | 主要损失原因 |
| --- | ---: | ---: | ---: | --- |
| 有效退款案件 | 10,000 | 100% | - | 进入统计范围 |
| 首次有效决定 | 9,210 | 92.1% | 790 | 订单匹配或必要事实不足 |
| 方案确认/明确替代方案 | 8,420 | 84.2% | 790 | 用户未接受扣费、材料未补齐 |
| 业务状态完成 | 7,110 | 71.1% | 1,310 | 供应商与人工协同未完成 |
| 到账/结果确认 | 6,580 | 65.8% | 530 | 支付渠道处理中或缺少用户确认 |
| 正确退款任务闭环 | 6,240 | 62.4% | 340 | 72 小时重复进线、事实或承诺不一致 |

### 8.4 核心指标矩阵

| 分组 | 指标 | Mock 当前值 | 目标/基线 | 状态 |
| --- | --- | ---: | ---: | --- |
| 业务结果 | 正确解决率 | 94.8% | ≥96.0% | 关注 |
| 业务结果 | 实际到账闭环率 | 92.5% | ≥95.0% | 关注 |
| 效率 | 首次有效决定时间 P50 | 42 秒 | ≤45 秒 | 正常 |
| 效率 | 最终到账时间 P50 | 2.1 天 | ≤2.0 天 | 关注 |
| 自动化 | 自动完成率 | 58.7% | ≥60.0% | 关注 |
| 体验 | 一次解决率 | 81.3% | ≥85.0% | 风险 |
| 体验 | 用户操作次数 | 1.6 次 | ≤1.5 次 | 关注 |
| 协作 | 供应商首次响应 P50 | 18 分钟 | ≤20 分钟 | 正常 |
| 协作 | 供应商 SLA 达成率 | 87.6% | ≥90.0% | 关注 |
| 质量 | 人工改判率 | 4.2% | ≤3.0% | 风险 |
| 风险 | 承诺失真率 | 0.36% | ≤0.20% | 风险 |
| 风险 | 错误退款/重复赔付率 | 0.03% | ≤0.02% | 风险 |
| 风险 | 该转人工未转率 | 0.8% | ≤0.5% | 风险 |

效率指标必须标注 P50/P90；风险指标的下降才是改善；所有指标都允许展开查看分母和事件定义。

### 8.5 Badcase 闭环工作台

Badcase 不只是异常列表，必须呈现完整生命周期：

```text
发现 → 归因 → 修复 → 回归验证 → 上线观察 → 关闭
```

看板顶部显示：闭环率、逾期数、复发率。队列字段包括：Badcase 类型、影响案件数、风险等级、当前阶段、Owner、SLA 和最近进展。

选中一个 Badcase 后，在同行下方展开：

1. 事实证据和关联 Trace；
2. 根因归属：Prompt、规则、Tool、数据、Workflow 或人工协同；
3. 修复动作及负责人；
4. 已加入的回归 Eval 用例；
5. 上线观察窗；
6. 可验证的关闭标准。

“已回复用户”或“已创建工单”不算 Badcase 闭环。只有修复上线、回归通过并在观察窗内未复发，才能标记关闭。

## 9. 响应式规则

- ≥1100px：场景、C 端任务和 Trace 三栏；
- 768–1099px：场景栏保留，Trace 进入抽屉；
- <768px：只显示 C 端任务，场景选择变为顶部下拉，主操作固定在底部；
- 面试官桌面默认打开演示模式；普通用户模式不渲染 Trace；
- 移动端按钮至少 44px，金额和操作不能被软键盘遮挡。

## 10. 与后端的映射

| 前端区域 | API / 数据 |
| --- | --- |
| A–L 场景选择 | `GET /api/scenarios` |
| 运行演示 | `POST /api/workflows/{scenario_id}/run` |
| 用户当前状态 | `case_status`、`waiting_for`、Tool 回执 |
| Agent Trace | `GET /api/workflow-runs/{run_id}` |
| Tool 审计展开 | `GET /api/traces/{trace_id}` |
| 不可逆操作 | `POST /api/confirmations` 后调用写 Tool |
| 运营看板 | `workflow_runs`、`tool_executions`、案件终态聚合 |

本地模式从 FastAPI 读取执行结果；GitHub Pages 使用同结构的浏览器 Mock Adapter。前端不自行拼接金额、退款状态或允许操作。

## 11. 实施建议

最终前端采用 React + TypeScript + Vite + 原生 CSS variables。视觉借鉴 shadcn/ui 的开放组件思路和 coss 的克制密度，但没有直接复制其组件代码或品牌外观。

第一轮实现顺序：

1. App Shell 与三模块路由；
2. Agent 设计流程图；
3. A–L 场景选择和后端执行；
4. C 端任务区与预期管理组件；
5. Trace 面板；
6. 运营看板；
7. 响应式、键盘和错误状态。
