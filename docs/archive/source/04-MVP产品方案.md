# 去哪儿酒店退款智能客服：MVP 产品方案

> 版本：v0.2  
> 日期：2026-09-04  
> 产品性质：求职作品集概念验证，不代表去哪儿真实产品、政策或业务数据  
> 产品角色：Agent 代表模拟的去哪儿酒店售后团队，直接服务 C 端用户

## 1. 为什么做这个 MVP

本项目的直接目标，是在一面后向面试官展示：候选人不仅理解“AI 客服”，还能够把酒店退款这种多方、强规则、强状态、涉及资金的售后问题，设计成一个可运行、可解释、可评测的 Agent 产品。

因此，MVP 不以“功能多”取胜，而要在 3–5 分钟内证明四项能力：

1. **需求分析能力**：识别用户表面问题背后的真实任务与体验断点；
2. **产品设计能力**：把规则、订单、退款状态和人工兜底组织成清晰流程；
3. **Agent 设计能力**：区分大模型、规则引擎、业务工具和人工分别负责什么；
4. **风险与评测能力**：对资金操作、错误承诺、越权和异常链路设置护栏。

## 2. 一句话产品定义

> 一个面向酒店订单用户的退款 Agent：自动理解诉求，读取模拟订单与成交政策，给出个性化退款方案，执行低风险退款任务，并把复杂争议连同完整上下文升级给人工。

它不是“酒店退款知识问答”，而是“能把退款案件往前推进的任务型 Agent”。

## 3. MVP 设计策略

### 3.1 全景场景库与分层实现

作品集 MVP 纳入用户场景地图中的 A–L 十二类场景，但不把“全部加入”理解为“全部自动化”。十二个场景按处理深度分为三层：

| 层级 | 场景 | 实现深度 | 展示价值 |
| --- | --- | --- | --- |
| 可自动闭环 | A 免费取消、B 扣费取消、C 退款未到账、I 订单变更 | 规则、Tool、确认和状态更新可完整运行 | 证明确定性自动执行与状态查询能力 |
| Agent 与外部协同 | D 到店前无房/加价、E 到店无房、F 不可取消例外、G 特殊原因、H 服务争议、J 资金异常 | Agent 完成识别、取证、建单、跟踪和人工衔接 | 证明多主体协作、风险控制与预期管理 |
| 专席路由 | K 跨境/多供应商、L 团队/企业/多房 | 完成责任链、授权与拆分预览后转专席 | 证明 Agent 知道自动化边界 |

分享时仍推荐以 F“不可取消订单例外协商”作为英雄场景，以 A、C、E 分别展示自动执行、资金状态和紧急履约；其余场景通过场景库进入。这样既保留 3–5 分钟的主叙事，也完整覆盖 A–L。

### 3.2 体验层与展示层分离

- **用户模式**：只呈现消费者需要的信息，语言简洁，直接给方案与操作。
- **演示模式**：可展开“Agent 如何判断”，显示意图、槽位、政策引用、规则校验、工具调用、风险等级和转人工原因。

演示模式是作品集解释层，不应直接照搬到真实 C 端产品。

## 4. MVP 范围

### 4.1 必须完成的 P0 能力

| 模块 | MVP 能力 | 用户价值 | 作品集价值 |
| --- | --- | --- | --- |
| 订单识别 | 登录态模拟、订单卡片、多个订单显式选择 | 不必手输全部信息，避免操作错单 | 展示上下文与强业务主键意识 |
| 意图识别 | 识别取消退款、退款进度、无法履约、人工投诉 | 快速进入正确流程 | 展示路由设计 |
| 关键信息补全 | 只追问会改变决策的原因、入住状态、期望方案 | 降低问询负担 | 展示槽位和多轮状态管理 |
| 个性化方案卡 | 展示可退金额、扣费、依据、到账时间和替代选项 | 一次看懂结果 | 展示从“回答”到“决策支持” |
| 低风险自动取消 | 二次确认后执行模拟取消与退款 | 直接完成任务 | 展示工具调用、权限与幂等 |
| 退款进度查询 | 区分退款申请、退款发起、渠道处理和到账 | 降低不确定性 | 展示业务状态建模 |
| 例外协商 | 自动生成协商申请、创建模拟供应商工单、跟踪结果 | 不必重复解释 | 展示多主体协同 |
| 到店无房紧急处理 | 紧急识别、人工入口、替代住宿/保障提示 | 优先保障当晚入住 | 展示风险分级和任务优先级 |
| 人工升级 | 自动生成案件摘要并保留上下文 | 不需向人工重述 | 展示完整人机协同 |
| 决策透明 | 用户可查看政策依据；演示者可查看完整决策轨迹 | 提升信任 | 展示可解释 Agent |

### 4.2 A–L 场景库的实现边界

- A、B、C、I 实现确定性计算、二次确认和 Mock 状态更新；
- D、E、F、G、H、J 实现端到端协同流程，但外部酒店、供应商、支付、审核与人工响应均为 Mock；
- K、L 实现责任链、授权和拆分预览，不自动执行跨境或团体订单写操作；
- 证明材料只保存 Mock 引用与结构化元数据，不处理真实医疗或证件材料；
- 场景看板和 bad case 面板需基于 Eval 与事件数据生成，不能先填无来源的漂亮数字。

### 4.3 明确不做

- 真实连接去哪儿、酒店、供应商或支付系统；
- 真实资金退款和赔付；
- 让大模型自主决定争议退款比例；
- 覆盖机票、火车票、门票等其他业务；
- 完整客服后台、供应商后台和财务系统；
- 复杂账号体系、生产级权限和大规模并发；
- 将模拟数据包装成去哪儿真实数据。

## 5. 四个重点演示场景

完整 A–L 场景脚本、状态流转与 Tool 顺序见 `11-A-L场景端到端演示脚本与状态流转.md`。本节保留四个重点场景，用于 3–5 分钟面试主线。

### 5.1 S1：不可取消订单例外协商——英雄场景

**用户输入**：“临时有事去不了了，酒店说不能退，能帮我处理吗？”

**模拟订单**：

- 国内酒店，2 晚，总价 ¥1,280；
- 距离入住还有 12 天；
- 成交政策为“预订成功 30 分钟后不可取消”；
- 用户在下单 2 小时后申请；
- 无入住、无历史退款、未向酒店发起过协商。

**Agent 流程**：

1. 从登录态候选订单中让用户确认目标订单；
2. 查询订单、成交政策快照和售后历史；
3. 识别这是“不可直接自动退款，但存在协商空间”；
4. 询问用户更倾向全退、部分退还是改期，并补充取消原因；
5. 生成结构化供应商协商单，而不是承诺退款；
6. Mock 供应商返回“可部分退款 ¥1,000”或“允许免费改期”；
7. 向用户展示并列方案、金额、依据和有效期；
8. 用户选择后执行模拟退款或改期；
9. 展示退款进度时间线。

**关键产品点**：

- 不把“不可取消”机械翻译为“不能退款”；
- 不由 LLM 自己计算或裁决退款金额；
- 清楚区分“已申请协商”“供应商已同意”“平台已发起退款”“资金已到账”。

### 5.2 S2：免费取消自动完成

**用户输入**：“取消明天去杭州的酒店。”

**模拟订单**：免费取消截止时间尚未到，总价 ¥688。

**Agent 流程**：

1. 识别并确认目标订单；
2. 调用政策与金额计算工具；
3. 展示“可退 ¥688、原路退回、预计 1–3 个工作日”；
4. 用户二次确认；
5. 调用模拟取消接口，返回退款单号；
6. 订单状态变为“已取消”，退款状态变为“已发起”。

**关键产品点**：金额透明、二次确认、操作幂等、状态可信。

### 5.3 S3：已退款未到账

**用户输入**：“三天前就说退款了，为什么还没收到？”

**模拟订单**：平台已于两天前发起退款，微信支付渠道处理中，承诺 1–3 个工作日。

**Agent 流程**：

1. 查询退款单与支付渠道状态；
2. 展示完整时间线；
3. 解释当前仍在正常 SLA 内，给出预计最晚更新时间；
4. 提供“到期未到账自动提醒并升级”操作；
5. 若切换异常数据，则自动创建支付调查工单。

**关键产品点**：解决“已退”和“到账”的语义混淆，不用空泛话术安抚。

### 5.4 S4：到店无房/被要求加价

**用户输入**：“我已经到酒店了，前台说没房，要加 300 元才给住。”

**Agent 流程**：

1. 立即识别为 `URGENT_FULFILLMENT_FAILURE`，不进入普通退款问答；
2. 确认用户已经到店、目标订单和联系方式；
3. 调用模拟酒店核验与附近替代住宿查询；
4. 同时展示人工加急入口；
5. 给出“协调原酒店”“更换附近同等级酒店”“取消并申请保障”三条路径；
6. 记录差价凭证要求与平台处理状态。

**关键产品点**：先解决当晚住宿，再处理责任和退款；正确转人工也算成功。

## 6. 用户端信息架构

### 6.1 页面结构

MVP 建议做成一个响应式单页应用：

```text
顶部：产品名 / “个人概念作品，数据均为模拟”标识 / 演示模式开关

左侧或顶部：场景切换
  - 不可退协商
  - 免费取消
  - 退款未到账
  - 到店无房

主区域：对话与任务卡
  - 用户与 Agent 对话
  - 订单确认卡
  - 退款方案卡
  - 证据/材料卡
  - 操作确认卡
  - 退款进度时间线

右侧抽屉（演示模式）：Agent 决策轨迹
  - 意图与风险等级
  - 已确认槽位/缺失槽位
  - 命中的政策及版本
  - 规则判断
  - 工具调用与结果
  - 自动执行/转人工原因
```

### 6.2 核心交互组件

#### 订单确认卡

- 酒店名称、城市、入住日期、房型、金额；
- 订单状态和退改标签；
- “确认是这笔”“不是这笔”操作。

#### 退款方案卡

- 主结论：可直接退款 / 需协商 / 退款处理中 / 紧急履约异常；
- 应退、扣费和补偿金额明细；
- 预计时间；
- 规则依据；
- 方案 A/B；
- 明确的下一步按钮。

#### 退款进度时间线

```text
退款申请已提交
→ 平台/供应商已确认
→ 平台已发起退款
→ 支付渠道处理中
→ 已到账
```

未知节点必须显示“待确认”，不能用完成态视觉误导。

#### 人工升级卡

- 转人工原因；
- 当前排队/预计响应时间（模拟）；
- 工单号；
- 已带给人工的事实和材料摘要；
- 用户无需重复说明的提示。

## 7. Agent 能力架构

### 7.1 分工原则

| 层 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| LLM | 意图识别、槽位抽取、多轮澄清、政策解释、摘要生成 | 金额计算、权限判断、最终退款裁决 |
| 规则引擎 | 条款时点、退款金额、风险等级、执行权限、转人工规则 | 理解复杂自然语言和情绪 |
| RAG/政策库 | 返回与订单版本、渠道和场景匹配的政策片段 | 直接做退款决定 |
| Mock 工具 | 查询订单/退款、执行模拟取消、创建工单、回传状态 | 根据自由文本自行猜测参数 |
| 人工 | 例外审批、事实冲突、高金额赔付、安全和法律争议 | 重复完成已能稳定自动化的低风险任务 |

### 7.2 Agent 工作流

```text
用户输入
→ 安全检查与登录态确认
→ 意图识别 + 紧急程度判断
→ 选择/确认订单
→ 查询订单事实、成交政策、售后与支付状态
→ 检查决策所需槽位
   ├─ 缺信息：只追问会改变结论的信息
   └─ 信息完整：进入规则判断
→ 生成候选方案
→ 金额、权限、风险硬校验
   ├─ 低风险且在授权内：向用户二次确认后执行
   ├─ 需要外部协商：创建供应商工单并跟踪
   └─ 高风险/冲突：携带摘要转人工
→ 更新案件与退款状态
→ 输出用户可理解的结论、依据、动作和时间
```

### 7.3 意图定义

```json
{
  "primary_intent": "CANCEL_REFUND | REFUND_STATUS | FULFILLMENT_FAILURE | ORDER_CHANGE | COMPLAINT | OTHER",
  "secondary_reason": "PLAN_CHANGE | ILLNESS | PRICE_CHANGE | NO_ROOM | PRICE_INCREASE | SERVICE_MISMATCH | PAYMENT_DELAY | UNKNOWN",
  "urgency": "NORMAL | HIGH | URGENT",
  "requested_outcome": "FULL_REFUND | PARTIAL_REFUND | CHANGE_DATE | REBOOK | STATUS_ONLY | HUMAN_HELP",
  "confidence": 0.0
}
```

意图置信度只决定是否需要澄清，不直接决定是否退款。

### 7.4 会话状态

```text
START
→ ORDER_PENDING_CONFIRMATION
→ FACTS_INCOMPLETE
→ READY_FOR_DECISION
→ OPTION_PRESENTED
→ USER_CONFIRMATION_PENDING
→ ACTION_SUBMITTED
→ WAITING_EXTERNAL
→ REFUND_PROCESSING
→ RESOLVED / ESCALATED / CANCELLED_BY_USER
```

会话状态与业务状态分开存储。用户退出对话不等于订单或退款终止。

## 8. Mock 工具设计

### 8.1 工具清单

| Tool | 输入 | 输出 | 主要用途 |
| --- | --- | --- | --- |
| `list_user_orders` | `user_id`, `status_filter` | 候选订单列表 | 关联登录态订单 |
| `get_order_detail` | `order_id` | 订单、渠道、供应商、支付概要 | 获取唯一事实 |
| `get_policy_snapshot` | `order_id` | 成交政策、版本、提示记录 | 防止引用当前网页规则 |
| `calculate_refund_quote` | `order_id`, `request_time`, `reason_code` | 可退、扣费、优惠分摊、方案 | 金额由确定性逻辑计算 |
| `submit_cancellation` | `order_id`, `quote_id`, `idempotency_key` | 取消结果、退款单号 | 低风险模拟执行 |
| `get_refund_status` | `refund_id` | 渠道状态、时间线、SLA | 退款进度查询 |
| `create_supplier_case` | 订单与结构化理由 | 工单号、SLA、状态 | 例外协商 |
| `get_alternative_hotels` | 城市、位置、等级、日期 | 替代住宿列表 | 到店无房恢复 |
| `create_human_handoff` | 案件摘要、风险、缺失信息 | 工单号、队列、预计响应 | 人工兜底 |

### 8.2 工具调用护栏

- 所有写操作必须包含 `idempotency_key`；
- 订单号只能来自已确认订单或用户显式输入；
- `submit_cancellation` 前必须存在未过期的 `quote_id`；
- 金额由工具返回，LLM 不允许自行修改；
- 真实执行前必须有用户二次确认；
- 工具失败时不能把预期结果写成已完成；
- 每次调用记录输入摘要、返回码、时间和 trace_id。

## 9. 模拟政策设计

首版不需要做庞大知识库，只需覆盖 A–L 的 13 条结构化模拟政策，并明确标注“模拟”。

### 9.1 结构化政策字段

```json
{
  "policy_id": "POL-HOTEL-CANCEL-001",
  "version": "2026.09-demo",
  "status": "ACTIVE",
  "channel_type": "DIRECT | AGENT | PACKAGE",
  "scenario": "FREE_CANCEL | TIERED_CANCEL | NON_REFUNDABLE | NO_ROOM | REFUND_SLA",
  "effective_from": "2026-09-01T00:00:00+08:00",
  "rule_expression": "...",
  "user_facing_text": "...",
  "requires_human": false,
  "source_label": "模拟政策，仅用于作品演示"
}
```

### 9.2 建议政策样例

1. 入住前一天 18:00 前免费取消；
2. 入住前一天 18:00 后扣首晚房费；
3. 预订成功 30 分钟后不可直接取消，可发起人工协商；
4. 疾病或交通中断材料只能触发审核，不能自动保证全退；
5. 到店前无房或加价进入履约保障流程；
6. 到店无房进入紧急人工队列；
7. 退款原路返回，模拟微信 1–3 个工作日、银行卡 3–7 个工作日；
8. 超过渠道 SLA 自动创建支付调查工单；
9. 超过订单金额的赔偿必须人工审批；
10. 重复退款、拒付或身份异常禁止自动执行。

## 10. Mock 数据集

### 10.1 最小规模

- 用户：12 个，每个场景 1 个演示用户；
- 酒店：12 家场景酒店 + 3 家替代酒店；
- 供应商：6 个；
- 订单：12 笔场景主订单，后续可增加干扰订单测试订单消歧；
- 退款单：1 笔初始退款 + 3 笔预期写入结果；
- 外部工单：9 笔供应商、支付、服务和专席工单 fixture；
- 模拟政策：13 条，包括退款 SLA；
- 离线 Eval：36 条，每个 A–L 场景 3 条；另有数据库、规则、权限、API 与 Workflow 自动化测试。

这组规模足够支撑演示和评测，不需要伪装成生产大数据。

### 10.2 十二笔场景主订单

十二笔订单统一使用 `ORD-A-001` 至 `ORD-L-001`，分别对应 A–L 场景；完整关联关系和预期路径见 `mock/scenario-fixtures.json`。

### 10.3 数据真实性声明

产品顶部、README 和详情页必须说明：

> 本项目为候选人个人概念作品。订单、政策、供应商回复、退款状态和指标均为模拟数据，不代表去哪儿网真实系统与经营情况。

## 11. 回复生成规范

### 11.1 标准结构

每个关键节点按以下顺序输出：

1. **结论**：当前能做什么；
2. **金额**：可退、扣费或差价；
3. **依据**：命中的成交政策/模拟保障；
4. **状态**：已经执行到哪里；
5. **时间**：预计下一更新或到账时间；
6. **选项**：用户接下来可以做什么。

### 11.2 示例

> 这笔订单仍在免费取消期内，可以退回 ¥688。退款将原路退回微信，预计 1–3 个工作日到账。现在还没有取消订单；确认后我才会提交。你可以选择“确认取消”或“保留订单”。

该表达同时避免了三种风险：没有替用户自动操作、没有把发起退款说成到账、没有隐藏金额与时限。

## 12. 风险分级与转人工规则

| 风险级别 | 条件 | 系统动作 |
| --- | --- | --- |
| L0 | 知识解释、无订单操作 | Agent 可直接回答，提供依据 |
| L1 | 条款明确、金额可计算、身份有效 | 二次确认后自动执行模拟操作 |
| L2 | 不可取消协商、材料审核、供应商待确认 | 创建工单，Agent 跟踪，不承诺结果 |
| L3 | 到店无房、高金额、政策冲突、支付异常 | 优先转人工，Agent 提供摘要与辅助工具 |
| L4 | 盗刷、欺诈、人身安全、诉讼/媒体、越权 | 立即阻断自动操作并升级专席 |

硬转人工触发条件优先于模型置信度和自动化目标。

## 13. 评测方案

### 13.1 离线测试集

当前已实现 36 条场景路由 Eval，并由自动化测试补充以下覆盖：

- 8 条意图与紧急程度识别；
- 8 条订单/槽位澄清；
- 8 条政策与金额决策；
- 6 条工具成功/失败/超时；
- 6 条安全、越权、重复执行和转人工边界。

### 13.2 关键指标

由于没有真实业务数据，MVP 只设置“演示验收目标”，不称为去哪儿业务指标：

| 指标 | MVP 验收目标 |
| --- | ---: |
| A–L 场景路由准确率 | 100%（固定回归集） |
| 退款金额计算正确率 | 100%（规则用例） |
| 写操作二次确认覆盖率 | 100% |
| 高风险场景转人工召回率 | 100%（固定回归集） |
| 重复退款成功次数 | 0 |
| 无依据“已退款/已到账”承诺 | 0 |
| 主流程工具成功率 | ≥ 95%（本地 Mock） |
| 主流程首屏响应 | ≤ 2 秒（本地 Mock） |

### 13.3 Bad case 分类

- 意图识别错误；
- 订单选错或未确认；
- 政策版本错误；
- 金额计算错误；
- 工具调用参数错误；
- 工具失败却宣称成功；
- 不该自动执行却执行；
- 应转人工未转；
- 状态表达误导；
- 用户体验冗长或重复追问。

## 14. 产品成功标准

### 14.1 演示成功

面试官在 3–5 分钟内能够看懂：

- 用户为什么需要这个产品；
- Agent 如何结合订单和政策做判断；
- 什么能自动做、什么必须转人工；
- 退款状态为什么是可验证的；
- 方案如何用评测和 bad case 继续迭代。

### 14.2 功能成功

- A–L 十二个场景都能从预置入口一键开始；
- 至少两条链路能更新真实的本地 Mock 状态；
- 每个结论能展开查看政策与工具依据；
- 刷新页面后当前订单/工单状态仍可保留；
- 异常工具响应有降级说明和人工入口；
- 所有模拟数据均有明确标识。

## 15. 建议技术实现

### 15.1 最小架构

```text
Web 前端
  → Agent Orchestrator
      → 意图/槽位抽取
      → 规则与风险引擎
      → 模拟政策检索
      → Mock Tool APIs
          - 订单
          - 退款
          - 供应商工单
          - 支付状态
      → 响应生成与事实校验
  → SQLite/JSON 状态存储
  → Trace 与 Eval 日志
```

### 15.2 实现原则

- 核心金额和状态流转采用确定性代码；
- 大模型不可用时，预置场景仍能靠规则模板演示；
- Agent 输出使用结构化 schema，再由前端渲染任务卡；
- Mock API 设计尽量接近真实业务接口，而非在前端写死全部结果；
- 保留 trace，便于向面试官展示一次请求如何完成。
