# 项目决策与个人贡献

## 项目性质

这是一个非官方个人产品设计与工程验证项目。订单、政策、供应商、接口、金额和运营指标均为 Mock，不代表去哪儿内部系统或真实业务效果。项目使用 AI 编程工具辅助资料整理、代码初稿和测试补充，但产品定义、边界选择、验收标准与最终结果由项目作者负责。

## 关键产品决策

| 决策 | 考虑过的方案 | 最终选择 | 选择原因 | 代价与局限 |
| --- | --- | --- | --- | --- |
| 产品目标 | 提升回答满意度 / 推进退款任务 | 正确退款任务闭环 | 用户需要可验证结果，不只是解释规则 | 需要连接更多业务状态和外部协作 |
| Agent 形态 | 自由 ReAct / 受控 Workflow | 显式状态机与受控 Workflow | 金额、政策和写操作错误成本高 | 灵活性低于开放式 Agent |
| 模型职责 | 模型直接决定 / 模型理解与表达 | LLM 只负责理解、抽取和表达 | 业务事实必须来自订单、规则和 Tool | 当前 Mock 未接入真实模型服务 |
| 政策处理 | 通用知识问答 / 订单级政策快照 | 订单事实加成交政策快照 | 同一酒店、房型和渠道规则可能不同 | 依赖真实系统提供可追溯快照 |
| 写操作 | Agent 自动执行 / 权限门与确认 | WRITE Gate、二次确认、版本和幂等 | 防止越权、重复退款和状态冲突 | 操作链路更长 |
| 风险兜底 | 尽量自动化 / 分级与人工接管 | L1 自动、L2 协作、L3 人工 | 高风险问题需要专业判断和授权 | 自动完成率不是唯一目标 |
| 演示范围 | 单一成功案例 / 十二类场景 | A–L 场景覆盖地图 | 同时验证正常、异常和复杂边界 | 场景 fixture 不能代表真实分布 |
| 在线部署 | 仅静态原型 / 前后端验证 | Pages 静态体验加本地完整后端 | 招聘方可立即体验，同时保留可执行工程证据 | 在线版本使用确定性 Mock Adapter |

## 个人负责范围

| 工作项 | 项目作者负责 | 可验证产物 |
| --- | --- | --- |
| 问题定义 | 明确用户任务、成功终点、非目标和风险边界 | 产品与需求分析、MVP 范围 |
| 场景建模 | 拆分取消、支付、履约和复杂订单场景并分级 | A–L 场景、fixture、成功断言 |
| 产品方案 | 设计用户方案卡、确认操作、状态反馈和人工接管 | React 三模块 Demo |
| Agent 架构 | 定义 LLM、规则、Tool、权限、Memory、Trace 和 Verifier 的职责 | Workflow 文档、Tool 契约、Schema |
| 数据与指标 | 设计 Mock 数据结构、北极星、漏斗、质量和风险指标 | SQLite Schema、运营看板 |
| 工程实现 | 确认前后端结构、接口、状态机和部署方式 | React、FastAPI、SQLite、GitHub Pages |
| 质量验收 | 定义业务不变量、评测集、失败路径和发布检查 | 36条 Eval、自动化测试、CI |
| 隐私边界 | 决定公开内容、脱敏方式和免责声明 | 匿名 fixture、README 声明 |

## AI 编程工具辅助范围

| 环节 | AI 工具辅助 | 作者必须完成的判断与验收 |
| --- | --- | --- |
| 资料整理 | 汇总公开资料、比较方案、整理文档初稿 | 核对来源、删除无依据结论、区分事实与假设 |
| 产品发散 | 补充场景、异常路径和备选交互 | 决定 MVP、优先级、风险分层和不做范围 |
| 代码实现 | 生成部分组件、接口、数据脚本和代码初稿 | 阅读代码、确定契约、调试状态、处理失败路径 |
| 测试 | 生成测试骨架和边界样例 | 定义业务不变量、补充高风险断言并执行测试 |
| 文档 | 调整结构、润色表达、生成图表草稿 | 保证内容与仓库实际实现一致 |

AI 工具没有替代业务判断，也不能成为“项目有效”的证据。可验证性来自运行结果、代码、测试、CI、数据边界和作者对关键取舍的解释能力。

## 验收方式

1. 每个场景必须到达预期案件状态；
2. 金额、状态和权限不得由展示文案自由生成；
3. 高影响写操作必须经过确认、版本校验和幂等控制；
4. L3 场景必须进入人工或专业队列；
5. 每个 Badcase 能回到场景、Workflow 节点、Tool 回执和规则版本；
6. README、在线 Demo、代码和面试陈述必须使用相同边界口径。

## 做过的返工

- 从“解释退款规则”调整为“推进退款任务到可验证结果”；
- 将退款成功拆成业务状态完成与资金到账两个终点；
- 将不可取消、到店无房、支付异常等场景从统一话术拆成独立 Workflow；
- 将人工接管从失败兜底改成正式产品路径；
- 将运营目标从回复率转为正确闭环、质量与风险共同约束。

## 当前未实现

- 真实大模型调用、Prompt 版本和线上模型评测；
- 真实订单、政策、供应商、支付和客服接口；
- 真实用户访谈结果和内部业务指标；
- 生产账号、权限审批、监控告警和灰度发布。

这些限制决定了项目可以证明产品设计和工程验证能力，但不能被描述为已上线的去哪儿业务系统或已经产生真实业务收益的产品。
