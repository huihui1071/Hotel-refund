# A–L 场景与 Eval

## 场景覆盖

| 场景 | 用户任务 | 风险 | 主要路径 | 成功终点 |
| --- | --- | --- | --- | --- |
| A | 条款内免费取消 | L1 | 确定性取消 | 订单取消并发起全额退款 |
| B | 明确扣费取消 | L1 | 报价 + 用户确认 | 用户明确接受扣费后执行 |
| C | 已退款未到账 | L1 | 退款/支付查询 | 给出真实渠道状态和 SLA |
| D | 到店前无房或加价 | L3 | 履约恢复 + 人工 | 替代方案或人工接管 |
| E | 到店后无房 | L3 | 紧急恢复 | 住宿恢复结果被确认 |
| F | 不可取消例外退款 | L2 | 供应商协商 | 用户选择返回的可行方案 |
| G | 疾病、灾害、交通中断 | L2 | 最少材料 + 例外审核 | 创建审核单，不提前承诺退款 |
| H | 描述不符或服务问题 | L3 | 证据 + 争议处理 | 当前住宿先被处理并升级审核 |
| I | 日期、姓名或房型订错 | L1 | 变更/取消方案比较 | 用户确认后完成变更 |
| J | 重复扣款或押金异常 | L3 | 支付语义识别 + 财务工单 | 区分扣款与预授权并进入调查 |
| K | 跨境或多供应商订单 | L3 | 责任链 + 专席 | 明确责任主体并携上下文升级 |
| L | 团队、企业或多房订单 | L3 | 拆单报价 + 专席 | 部分取消预览后由专席确认 |

每个场景都定义入口表达、订单与政策 fixture、必需 Tool、会话状态、案件状态、成功断言和失败兜底。数据入口见 [`mock/scenario-fixtures.json`](../mock/scenario-fixtures.json)。

## 为什么不是所有场景都自动退款

- L1 且事实、金额、权限完全确定时，可以在用户确认后执行；
- L2 需要外部协商或材料审核，Agent 负责建单、跟踪与呈现结果；
- L3 涉及紧急履约、资金争议、跨境责任链或团体授权，优先人工召回；
- “转人工”不是失败，丢失上下文、错误承诺或该转未转才是失败。

## 当前 Eval

[`eval/agent-eval-cases.json`](../eval/agent-eval-cases.json) 包含 36 条中文用户表达，每个 A–L 场景 3 条。当前自动验证：

- 场景路由准确性与 A–L 覆盖完整性；
- 风险等级是否存在；
- Workflow 是否调用正确 Tool 序列；
- 金额、订单、退款、案件和外部工单是否到达预期状态；
- 权限拒绝、重复写入、版本冲突和未知结果是否被正确处理。

整个后端目前包含 61 项自动化测试。运行：

```bash
cd backend
UV_CACHE_DIR=/tmp/hotel-refund-uv-cache uv sync --extra dev
.venv/bin/pytest -q
```

## 在线与本地演示边界

GitHub Pages 为免安装体验，使用与正式响应结构一致的浏览器端确定性 Mock Adapter；本地模式连接 FastAPI，实际执行 SQLite、规则引擎、Tool 权限网关和 Workflow。在线演示用于展示产品体验，本地测试用于验证业务逻辑，两者均不连接真实业务系统。
