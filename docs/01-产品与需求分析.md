# 产品与需求分析

## 一句话定义

Agent 代表模拟的酒店售后团队，在订单、成交政策、责任主体和授权边界明确后，以最少交互给 C 端用户结论和可执行方案，并把取消、退款、履约恢复或人工协同推进到可验证结果。

## 问题定义

用户表面上常问“能不能退”“多久到账”，真正需要完成的是一次售后决策：

- 当前订单是否允许取消、会扣多少、能退多少；
- 标准政策不能满足时，是否存在改期、协商或住宿恢复方案；
- 当前由平台、酒店、供应商、支付渠道还是人工专席负责；
- 任务是否真实推进，何时更新，用户还需要做什么。

传统 FAQ 或纯对话机器人只能解释通用规则，无法可靠处理成交政策快照、动态订单状态、资金动作和跨主体协作。因此本项目把“正确推进任务”而不是“完成一次回复”作为产品目标。

## 用户与关键场景

直接用户是遇到行程变化、退款等待或酒店履约异常的 C 端消费者。按任务和风险将场景归为四组：

1. **取消与变更**：免费取消、扣费取消、不可取消例外协商、特殊原因审核、日期/姓名/房型变更。
2. **退款与支付**：退款未到账、重复扣款、押金或预授权异常。
3. **履约异常**：到店前无房或加价、到店后无房、描述不符或服务问题。
4. **复杂订单**：跨境多供应商、团队/企业/多房订单。

## 核心洞察

1. 用户问规则，实际需要的是基于自己订单的决定和下一步。
2. 不确定性比金额本身更容易引发重复进线；必须说明已发生什么、等待谁、何时更新。
3. 退款不一定是最优路径，改期、替代住宿和供应商协商可能更接近用户原始目标。
4. 自动化边界取决于事实能否验证、金额能否确定、权限能否授权，而不是模型表达是否流畅。
5. “已发起”不能包装成“已完成”；到账和外部协同必须等待真实终态或用户确认。

## MVP 范围

### P0

- 识别问题类型、原因、紧急度并关联唯一订单；
- 读取订单、政策、售后、退款、支付和供应商事实；
- 生成确定性金额或变更报价；
- 给出结论、可执行方案、影响和预计时间；
- 对低风险写操作获取用户确认后执行；
- 对复杂案件创建供应商、支付或人工工单并持续跟踪；
- 保存 Session、Case Event 和 Tool Trace，支持恢复与质检。

### 不做

- 不接入真实去哪儿订单、政策、供应商或支付系统；
- 不模拟真实业务成绩，不宣称线上经营效果；
- 不让 LLM 自行决定退款金额、补偿额度或操作权限；
- 不以聊天轮次、机器人回复率或未转人工率替代业务结果指标。

## 产品成功标准

- 用户能在当前页面明确知道结论、金额影响、下一步和更新时间；
- 低风险任务能完成确定性操作，高风险任务能携带上下文顺畅升级；
- 所有展示金额和状态都有 Tool 或规则依据；
- A–L 场景均有成功终点、失败兜底和可复现 Mock 数据；
- 运营侧能定位链路流失、质量风险并推动 Badcase 修复闭环。

## 已确认与待真实验证

已确认的是产品对象、体验原则、Workflow 边界和演示范围。订单数据、政策、接口、供应商 SLA、指标目标值和样本分布均为模拟；真实上线前必须通过业务数据、客服访谈、法务/合规评审和灰度实验重新验证。
